🏗 2. Architecture
🔄 System Overview
Pulsar is organized in layers. You interact through one of four interfaces (TUI, CLI, REST API, Web UI), which call into the executor layer. The executor dispatches to the appropriate backend — Proxmox REST API, libvirt, Ansible, Terraform, or Packer.
Directory Structure
pulsar/ ├── shared/ ├── proxmox/ │ ├── bash/ (22) · python/ (27) │ ├── ansible/ (17) · terraform/ ├── kvm/ │ ├── bash/ (14) · python/ (19) │ └── ansible/ (5) ├── packer/ (6) ├── go/ (4 binaries) ├── web/ (SvelteKit) ├── tests/ (30 files) └── docs/
Design Principle
proxmox/ — PVE only
kvm/ — libvirt only
shared/ — usable by both

🌐 8. API Gateway
The API Gateway (apigateway) exposes all functionality as a RESTful JSON API on :8443. Start with ./bin/apigateway.exe or make api.
🔐 Authentication
The API supports two authentication methods. Include your credentials in every request via the Authorization header.
Method 1: X-API-Key
curl -X GET "https://localhost:8443/api/v1/vms" \ -H "X-API-Key: your-api-key-here" \ -H "Content-Type: application/json"
Simple API key authentication. Generate keys via apigateway --generate-key.
Method 2: Bearer Token
curl -X POST "https://localhost:8443/api/v1/auth/login" \ -H "Content-Type: application/json" \ -d '{"username":"admin","password":"secret"}' # Returns: { "token": "eyJhbGciOiJIUzI1NiIs..." }
curl -X GET "https://localhost:8443/api/v1/vms" \ -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."
JWT tokens expire after 24 hours by default.
CORS: Enabled by default with wildcard origin. Configure in settings.yaml under api.cors.
TLS: The server requires TLS. Generate self-signed certs with make certs or provide your own in settings.yaml.

💾 13. Backup & Restore
Pulsar integrates Proxmox Backup Server (PBS) for efficient, deduplicated backups with push-based architecture and incremental snapshots.
⚙ PBS Configuration
proxmox-backup-server: host: "10.0.0.10:8007" datastore: "main" fingerprint: "xx:xx:xx:xx:xx" username: "root@pam" password: "" namespace: "production"
Retention Policy
• Keep last 7 daily backups
• Keep last 4 weekly backups
• Keep last 12 monthly backups
• Keep last 3 yearly backups
▶ Backup Commands
$ pmxctl backup run --all # backup all VMs
$ pmxctl backup run 100 101 102 # backup specific VMs
$ swissknife backup run --all # unified backup
$ pmxctl backup list # list recent backups
$ pmxctl backup status <backup-id> # backup status
$ pmxctl backup restore <backup-id> --node pve1 # restore backup
🚨 Disaster Recovery
Node Failure
1. Restore VMs from PBS onto a healthy node
2. Rejoin cluster with pmxctl cluster join
3. Reconfigure HA groups
Full Cluster Loss
1. Reinstall Proxmox on all nodes
2. Restore PBS configuration from backup
3. Restore VMs via pmxctl backup restore
Always test a restore in a staging environment. Automate nightly backups with pmxctl backup run --all --cron "0 2 * * *".

🔒 15. Security
🔐 Authentication Methods
API Keys
Static pre-shared keys. Generate with apigateway --generate-key. Store in environment variables or settings.yaml.
JWT Tokens
Time-limited bearer tokens (24h default). Issued via POST /api/v1/auth/login. Refresh with POST /api/v1/auth/refresh.
mTLS
Optional mutual TLS for machine-to-machine auth. Requires client certificates signed by the internal CA.
Secrets Management
• HashiCorp Vault integration via PULSAR_VAULT_ADDR
• SOPS-encrypted YAML files for GitOps
• Environment variable substitution in YAML
• TLS 1.3 for all API communication
Encryption
• TLS 1.3 for API Gateway
• AES-256-GCM for backup encryption
• SSH key-based auth for Ansible
• API tokens scoped by RBAC role
🛡 Security Best Practices
1. Use API tokens instead of passwords for Proxmox authentication
2. Enable PULSAR_PROXMOX_INSECURE=false in production
3. Restrict API keys with IP whitelisting and RBAC scopes
4. Run Ansible hardening roles against all Proxmox and KVM hosts
5. Rotate secrets regularly — use Vault or SOPS for GitOps
6. Enable audit logging and forward to centralized SIEM

📋 17. Runbooks
Runbooks provide step-by-step procedures for common operational scenarios. Always verify the environment state before executing destructive actions.
🚨 Runbook A: Node Failure Recovery
Symptoms
• Node unreachable via SSH and web UI
• Cluster shows node as offline/inactive
• HA services fail over but may stall
Step 1: Verify Node Status
# Check cluster status from a healthy node
$ pmxctl cluster status
If node shows offline, proceed to Step 2.
Step 2: HA Failover
$ pmxctl ha group list # check HA groups
$ pmxctl ha resource status # check resource state
$ pmxctl ha resource migrate <vm> --node <node> # manual migration
Step 3: Recover Node
• Power cycle and check console
• If hardware failure: replace hardware, reinstall Proxmox
• Rejoin cluster: pmxctl cluster join <node>
• Restore corosync config from backup if needed
Step 4: Verify Recovery
$ pmxctl cluster status # all nodes online?
$ pmxctl vm list # all VMs running?
🗄 Runbook B: Storage Full
Symptoms
• Alerts: storage usage > 90%
• VM disk errors or I/O pauses
• Backup jobs failing with "no space"
Step 1: Identify Usage
$ pmxctl storage list # list all storage pools
$ pmxctl storage info local-lvm # check specific pool
$ pmxctl storage content local-lvm # find large volumes
Step 2: Free Space
• Remove old backups: pmxctl backup prune --keep 7
• Delete unused ISO templates
• Relocate large VMs to another storage
Step 3: Add Capacity
• Add new disk to ZFS pool
• Expand LVM logical volume
• Configure PBS for off-site backups

📋 17. Runbooks (cont.)
🔄 Runbook C: Failed Migration
Symptoms
• Migration task fails with error message
• VM stuck in "migrating" state
• Network connectivity issues between nodes
Step 1: Check Migration State
$ pmxctl vm status <vmid> # check current state
$ pmxctl node tasks <node> # view task logs
If VM is stuck, you may need to unlock it.
Step 2: Unlock & Cleanup
$ pmxctl vm unlock <vmid> # unlock VM if locked
$ pmxctl vm migrate <vmid> --cancel # cancel ongoing migration
Step 3: Retry Migration
# Try offline migration first:
$ pmxctl vm shutdown <vmid> --force
$ pmxctl vm migrate <vmid> --target <node> --online=false
# Then restart on target:
$ pmxctl vm start <vmid>
Prevention
• Ensure shared storage is available on both nodes
• Check network latency between nodes (ping)
• Verify CPU compatibility (or use --force-cpu)
♻ Runbook D: Backup Recovery
Scenario
A VM has failed or been corrupted. You need to restore from the latest PBS backup.
Step 1: List Available Backups
$ pmxctl backup list --vmid <vmid> # list backups for VM
$ pmxctl backup info <backup-id> # backup metadata
Step 2: Restore
# Restore to original node:
$ pmxctl backup restore <backup-id> --node pve1
# Or restore with new VMID (avoids conflicts):
$ pmxctl backup restore <backup-id> --node pve1 --newid 300
Step 3: Verify Restore
$ pmxctl vm start <vmid> # start restored VM
$ pmxctl vm status <vmid> # verify running
SSH into the VM and verify application health.
Always verify backup integrity with pmxctl backup verify <backup-id> before relying on a restore.
